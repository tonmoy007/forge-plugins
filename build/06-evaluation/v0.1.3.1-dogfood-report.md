## Findings

### EF-021 — Test suite depends on `python-frontmatter` (test_force_advance.py)

Four test methods in `tests/unit/test_force_advance.py` do `import frontmatter` directly instead of using `_state_lib.read_state()` / `_split_frontmatter()`:

- `TestStageAdvancement::test_increments_by_one`
- `TestStageAdvancement::test_jumps_to_explicit_stage`
- `TestHistoryRow::test_force_marker_added`
- `TestHistoryRow::test_long_reason_truncated_in_history`

- **Category**: bug (test dependency leak)
- **Bucket**: hotfix-now → **resolved in this session**
- **Rationale**: v0.1.3.1 (commit d861ffb) removed `python-frontmatter` from all production code paths, but these 4 test methods retained the import. Any system without `python-frontmatter` installed (expected for external users who only install `requirements.txt`) sees 4 failures out of 695 unit tests. The fix replaces `import frontmatter; post = frontmatter.load(...); assert post["field"]` with `state = _state_lib.read_state(...); assert state["field"]` and `_, body = _state_lib._split_frontmatter(...)` — both already available in the scripts path. Also fixed import ordering (`import _state_lib` after `sys.path.insert` for the scripts dir).
- **Result**: 695/695 pass without `python-frontmatter` installed (previously 691/695).
- **Mirrors to**: shipped in this session.

### EF-022 — `post-tool-use.py` crashes on string `tool_input`

```
File "hooks/post-tool-use.py", line 116, in main
    file_path = tool_input.get("file_path", "")
AttributeError: 'str' object has no attribute 'get'
```

- **Category**: bug
- **Bucket**: hotfix-now → **resolved in this session**
- **Rationale**: The hook unconditionally calls `.get()` on `tool_input`, but the event payload carries `tool_input` as a plain string when Claude Code runs a non-Write tool (e.g., `Bash`, `Read`). The `tool_response` field has the same shape inconsistency — it can be a plain bool or a dict. Fixed with `isinstance()` guards in both fields. Error was silently logged to `.forge/hook-errors.log` (hook runner catches all exceptions) and the hook continued with empty `file_path`, so no session blocked — but the error log would confuse users during debugging.
- **Result**: Post-fix: hook handles both `str` and `dict` `tool_input`, no error written to log.
- **Mirrors to**: shipped in this session.

### EF-023 — `pre-tool-write.py` crashes on string `tool_input`

```

AttributeError: 'str' object has no attribute 'get'
```

### EF-024 — Hook errors persist in `.forge/hook-errors.log` after fix

Pre-fix hook crashes (EF-022, EF-023) are appended to `.forge/hook-errors.log` as JSONL. After applying the fix, the old errors remain in the log. `/forge:doctor` reads this log and warns about old, already-fixed errors.

- **Category**: friction
- **Bucket**: fix-v0.1.5
- **Rationale**: Doctor reports old errors from a session that is now fixed. The error log is append-only — no pruning or TTL. A user who upgrades mid-project will see stale error warnings. Suggest either: (a) bump the log format to track fix version, (b) add `doctor --clear-errors` flag, or (c) rotate the log on doctor run.
- **Mirrors to**: REQ-ERRORLOG-001 (new)

### EF-025 — Detect script returns `unknown` with 0% confidence for small projects

`scripts/detect-project-type.py` returns `{"type": "unknown", "confidence": 0.0, "indicators": ["no recognizable project files found"]}` for projects under ~50 LOC with no package manifest. The skill init flow handles this via user prompt, but the fallback path (ask user → manual set) adds friction.

- **Category**: friction
- **Bucket**: fix-v0.1.5
- **Rationale**: A `script` profile exists in the agent set but the detect script never suggests it — it only returns `unknown`. Per `forge-init/SKILL.md`, `suggested_profile: "script"` is supposed to fire for small projects (<500 LOC, no package manifest) but the detect script doesn't implement this logic. The fallback user prompt works but the first impression for a small CLI/script project is "Forge can't figure out what this is."
- **Mirrors to**: REQ-DETECT-001 (new)

### EF-026 — `check_srs_acceptance.py` and 15 other gate scripts don't exist

`references/gate-criteria.md` references **16 distinct `script_returns_zero` scripts** across stages 1–12. Only **1 of 16 exists** (`check_dir_nonempty.py`). The remaining 15 are stubs that degrade to `warning` severity, silently weakening every gate that depends on them.

Already documented in EF-019's audit (2026-06-01). This run corroborates: G1-003, G4-004, and all other script-return gates produce the same `"check script not yet implemented"` message. The gate produces a "green" verdict for blockers while the substantive check never runs.

- **Category**: bug (already tracked as EF-019)
- **Bucket**: fix-v0.1.5 (already tracked)
- **Rationale**: Corroborating data point from a second tester. EF-019 calls this "the gate-config layer is mostly decorative across the entire pipeline" — this run confirms that assessment. Gates are purely structural (file-exists, file-contains) except at the edges; every semantic check is unimplemented.
- **Mirrors to**: already tracked in srs-v0.1.5.md REQ-GATESTUB-001

### EF-027 — `session-start` hook shows "0 active lessons" even when `lessons.yaml` has entries

After `force-advance` recorded a lesson to `.forge/lessons.yaml`, the `session-start` hook still printed `[Forge] Active lessons (0): (none)` on the next invocation.

- **Category**: bug
- **Bucket**: fix-v0.1.5
- **Rationale**: The hook reads `lessons.yaml`, counts entries where `frequency > 0` or a certain `active` flag is set. The lesson recorded by `force-advance` had `frequency: 1` and no `active: true` field — so the counter returned 0. Either the lesson schema needs an `active` marker, or the hook's active count logic needs to include frequency≥1 entries.
- **Mirrors to**: REQ-LESSONCOUNT-001 (new)
