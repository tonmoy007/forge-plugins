### EF-002 — state-manager AttributeError on `frontmatter` module

> `python3 .../state-manager.py set --field project_type --value ml-pipeline …`
> `AttributeError: module 'frontmatter' has no attribute 'load'`

- **Category**: bug
- **Bucket**: `hotfix-now` → **resolved in v0.1.3.1**
- **Rationale**: PyPI package collision — wrong `frontmatter` package
  shadowed `python-frontmatter`. Same root cause as EF-001; same fix.
- **Mirrors to**: shipped — `CHANGELOG.md [0.1.3.1]`
- **Corroborating evidence** (2026-05-24): Tester shared their
  per-project `error_logs.jsonl` showing **28 `state_read_failed`
  events** between 2026-05-23 09:44 UTC and 2026-05-24 09:42 UTC, all
  carrying `detail: "module 'frontmatter' has no attribute 'load'"`.
  Frequency ~1 per 5–15 minutes during active sessions. This means
  every state-dependent hook silently failed throughout the tester's
  ~24-hour evaluation window. Verified post-hoc that v0.1.3.1 has zero
  `frontmatter` runtime imports in `hooks/`, `scripts/`, `agents/`, or
  `skills/`; only the test-only dep remains in `requirements.txt`.
  Last error timestamp is 17 minutes after the v0.1.3.1 tag, so the
  tester had not yet upgraded.

### EF-003 — External `security_reminder_hook.py` false positives on prose (paraphrased)

(paraphrased) Tester reports that on every `Write` to a `.md` file under
the spec/arch/plan stages, an external PreToolUse hook named
`security_reminder_hook.py` emits warnings about code-execution APIs
(the dynamic-code-evaluation built-in, and the Python serialization
module starting with "p"). The warnings fire because prose discussion of
those APIs trips a naive keyword matcher.

- **Category**: bug (external) — **escalated** 2026-05-24 from
  "annoying" to "trains tool-bypass behavior"
- **Bucket**: `defer-out-of-scope` (Forge can't fix another plugin's
  hook) **but** the Forge-side response (REQ-DOCS-001) is priority-bumped
- **Rationale**: `security_reminder_hook.py` is **not** part of Forge.
  Forge's only PreToolUse hook is `hooks/pre-tool-write.py`. The warning
  hook belongs to a separately installed plugin doing keyword matching
  on `.md` files. Forge cannot fix another plugin's hook.
- **Action**: Add a troubleshooting note pointing users at `/plugin list`
  to identify the source. (This finding even fired during the writing of
  this very file — the literal verbatim quotes had to be paraphrased to
  let the file be saved.)
- **Mirrors to**: `srs-v0.1.5.md` REQ-DOCS-001
- **Corroborating evidence — bypass behavior** (2026-05-24, post-v0.1.3.1
  spec session): During `/forge:spec`, the tester's Claude session hit
  the false-positive block on three `Write` calls in a row. The model's
  literal in-transcript statement was *"Let me write the files using
  bash to bypass the false positive warnings"*, after which it issued
  `cat > path << 'EOF' ...` heredoc writes via the `Bash` tool. Three
  downstream concerns escalate this beyond cosmetics: (1) heredoc writes
  bypass *all* `PreToolUse:Write` hooks including legitimate ones, not
  just the misfiring one; (2) repeated false positives train a "when
  blocked, escape via bash" reflex that would also bypass a true
  positive; (3) the audit trail loses fidelity — file writes appear as
  opaque `Bash` events instead of `Write` events. REQ-DOCS-001 stays
  the disposition, but priority is bumped to **top of v0.1.5 docs work**
  because every day this lives without a warning costs trust in the
  tooling layer.
- **Corroborating evidence — bash-heredoc bypass** (2026-05-24):
  During the post-v0.1.3.1 `/forge:spec` session, three `Write` calls
  to `04-spec/` markdown files were blocked by the external hook.
  The LLM verbatim decided: *"Let me write the files using bash to
  bypass the false positive warnings"* and used `cat > path << 'EOF'`
  heredocs to produce the same content. Consequences:
  - **Observability loss**: writes that should appear as `Write` tool
    events appear as opaque `Bash` events; legitimate PreToolUse hooks
    don't see them either.
  - **Pattern training**: every false-positive block reinforces "when
    blocked, escape via bash." If a real positive ever comes through,
    the trained reflex is already to bypass.
  - **Audit trail rot**: file content provenance is harder to
    reconstruct from tool-call logs.
  This makes EF-003 a *user-environment-level* concern, not a cosmetic
  one. REQ-DOCS-001 should be near the top of v0.1.5 doc work.

### EF-017 — `/forge:doctor` reports healthy while current-stage gate is wedged

(paraphrased) In the same v0.1.3.1 session that surfaced EF-005's
wedge, the tester ran `/forge:doctor` first and got *"Result: all
checks passed. Your Forge installation is healthy."* They then ran
`/forge:status`, which showed `0/4 gate criteria passed (3 blocker
failures)` for stage 4. Two diagnostics, same session, contradictory
verdicts.

- **Category**: bug
- **Bucket**: `fix-v0.1.5`
- **Rationale**: `doctor.py`'s check set covers environment (Python,
  PyYAML, Claude Code version), plugin (manifest, hook count, agent
  count, gate criteria parse), project (writability, current stage,
  gitignore), and global (writable, disk free, hook errors recorded).
  It does **not** check "is the current stage's exit gate satisfied?"
  — the single most important diagnostic about whether the pipeline
  can move forward. So a wedged session shows green.
- **Relation to REQ-SILENTSTATE-001**: Same antipattern family —
  surface-level "healthy" while the underlying system is stuck. Distinct
  REQ because the fix is additive (run gate check inline in doctor)
  rather than a failure-handling rewrite.
- **Mirrors to**: `srs-v0.1.5.md` REQ-DOCTOR-001

### EF-020 — `/forge:build` has no milestone or batch mode; one invocation per task

(paraphrased) Tester asked how to complete *"one milestone or multiple
milestones in one command"* — currently they must run `/forge:build`
once per task. With the in-repo DAG containing 33 tasks across 7
milestones, that's 33 invocations to ship the plugin itself.

- **Category**: friction (UX gap; data model supports milestones but
  the builder skill ignores them)
- **Bucket**: `fix-v0.1.5` (blocked on **OQ-8** — see srs-v0.1.5.md)
- **Severity**: low-medium — no correctness bug, but a real friction
  multiplier on plans with many tasks. Fatigue compounds with EF-013
  ("agents should be more interactive") — long task chains amplify
  whatever UX rough edges exist per task.
- **Rationale**: `skills/forge-build/SKILL.md` is explicit: pre-flight
  reads progress.md to identify *the current* task, runs one Builder
  pass, marks one task done, and the footer says *"Run `/forge:build`
  again for the next task."* No `--milestone`, `--batch`, or `--all`
  flag. The planner already emits milestones — `build/04-plan/task-dag.md`
  has `## Milestone 1: Core Skeleton`, `## Milestone 2: Hook System`,
  etc., with multiple T-IDs grouped under each. `agents/planner.md:55`
  says *"Define milestones (logical completion points, not arbitrary
  dates)."* So milestones are first-class in the data model and in the
  planning agent's mental model, but the builder treats the DAG as a
  flat task list. That mismatch is the bug.
- **Design tension** (why this isn't an obvious add): per-task
  atomicity is intentional in Forge — atomic commits per T-ID, gate
  checkpoints between tasks, bounded LLM context per task. A naive
  `--all` flag would erode all three. A disciplined `--milestone N`
  flag that still commits/gates per task and pauses on failure
  preserves the discipline while removing the typing overhead.
  Decision lives in OQ-8.
- **Mirrors to**: `srs-v0.1.5.md` REQ-BUILDBATCH-001 (+ OQ-8)

### EF-019 — Stub gate checks degrade to warning, hide unimplemented coverage verification

(paraphrased) Tester ran `/forge:spec` (or stage-4 gate check) on
v0.1.3.1 and the output reported *"3/4 passed (all blocker criteria
met)"* with G4-004 flagged ⚠️ *"check script not yet implemented:

- **Severity**: medium — visible warning (unlike [[ef-017]] doctor

  the one criterion that does semantic verification (architecture →

- **Rationale**: `references/gate-criteria.md:209-215` declares G4-004
  *"Spec covers all components from architecture"* via

  missing script to `(False, "check script not yet implemented: …")`
  and — because severity is `warning` — the gate still reports all
  blockers met. Net effect: stage 4's coverage check is the substantive
  gate; without the script, G4 reduces to "three files exist" rather
  than "spec covers architecture."
- **Audit result** (2026-06-01): `references/gate-criteria.md`
  references **16 distinct `script_returns_zero` scripts**; only
  **1 of 16 exists** in `scripts/`. Existing: `check_dir_nonempty.py`.
  Missing (15): `check_srs_acceptance.py`, `traceability-check.py`
  (referenced 4×), `spec-coverage.py`, `check_dag_completeness.py`,
  `check_dag_completion.py`, `token-audit.py`, `check_coverage.py`,
  `check_todos.py`, `check_progress_sync.py`, `check_nfr_coverage.py`,
  `check_open_bugs.py`, `check_health.py`, `check_hotfix_tests.py`,
  `check_git_tag.py`, `some_check.py`. Net effect: virtually every
  `script_returns_zero` check across stages 1–12 is currently a no-op
  that degrades to a `warning` — the gate-config layer is mostly
  decorative across the entire pipeline, not just stage 4.
- **Relation to antipattern family**: Same family as
  [[ef-007]] (REQ-SILENTSTATE-001), [[ef-017]] (REQ-DOCTOR-001),
  [[ef-018]] (REQ-LESSON-SOURCES-001) — surface looks fine, substantive
  check is silently inert. Distinct REQ because the fix is either
  (a) implement the missing script(s) + bump to blocker, or (b)
  fail-loud on any `not-yet-implemented` check until the script lands.
- **Mirrors to**: `srs-v0.1.5.md` REQ-GATESTUB-001 (+ OQ-7 for the
  fail-loud-vs-implement-first decision)

### EF-018 — Lesson capture trigger surface is too narrow

(paraphrased) Tester reported their project's `.forge/lessons.yaml`
showed `schema_version: 1, lessons: []` after a multi-error
`/forge:spec` session containing path collisions, security-hook
bypasses, stale-artifact cleanup, and explicit LLM strategy shifts.
Expectation was that some lesson would have been captured.

- **Category**: bug (design — narrow trigger)
- **Bucket**: `fix-v0.1.5`
- **Rationale**: Per ADR-002 and `scripts/extract-lessons.py`, lesson
  capture works as follows: `prompt-submit.py` watches user prompts for
  explicit correction patterns (`don't X`, `use X not Y`, `always X`,
  `prefer X`); matches become rows in `.forge/correction-flags.jsonl`;
  the extractor rule-matches each flag and appends to `tasks/lessons.md`;
  `sync-lessons.py` mirrors that into `.forge/lessons.yaml` on
  `SessionStart`. So `lessons: []` is the **architecturally correct
  output** for a session in which the user never typed a correction —
  but that means Forge only learns from *explicit* user complaints,
  never from *observable* session pathologies (hook errors, tool
  fallback patterns, contradictory diagnostics, agent self-correction,
  stage wedges). The bug is the narrow trigger surface, not the
  extractor itself.
- **Mirrors to**: `srs-v0.1.5.md` REQ-LESSON-SOURCES-001 (+ OQ-6 for
  the signal-selection cutoff)
